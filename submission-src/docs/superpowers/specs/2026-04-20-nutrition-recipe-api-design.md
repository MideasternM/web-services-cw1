# Nutrition and Recipe Analytics API Design

**Goal:** Build an individual FastAPI-based web API backed by SQLite that supports full CRUD for nutrition-related data, provides analytics endpoints, and is packaged with documentation, testing, and presentation materials suitable for the XJCO3011 Coursework 1 oral examination.

**Target grade:** 70+ by delivering clean modular code, comprehensive documentation, clear version-control evidence, consistent testing, and an implementation that goes beyond basic CRUD through analytics and lightweight authentication.

## 1. Problem Definition

The project will implement a Nutrition and Recipe Analytics API. The API will allow a client to manage recipes and ingredients, link ingredients to recipes with quantities, and calculate nutrition summaries from stored data. The design is intentionally centered on a domain where CRUD operations are natural, relational database structure is meaningful, and analytical endpoints can be demonstrated clearly in the oral examination.

The project is designed to satisfy the coursework brief while staying scoped for reliable implementation. It will meet the minimum technical requirements through SQL-backed CRUD operations and HTTP-accessible endpoints, then extend beyond that baseline through category analytics, nutrition aggregation, filtered search, documentation, testing, and a lightweight API key authentication scheme for write operations.

## 2. Scope

### In scope

- Build a REST API using FastAPI.
- Use SQLite as the project database.
- Model recipes, ingredients, and recipe-to-ingredient relationships in SQLAlchemy.
- Implement CRUD operations for recipes and ingredients.
- Implement create and delete operations for recipe-ingredient associations.
- Expose analytics endpoints for nutrition totals, category counts, and filtered recipe search.
- Protect write operations with a simple API key mechanism.
- Generate API documentation through FastAPI OpenAPI support and package it as PDF for submission.
- Add automated tests with pytest.
- Prepare repository structure to support README, technical report, and presentation materials.

### Out of scope

- Full user registration and login flows.
- Role-based authorization.
- Remote third-party API integration at request time.
- Heavy dataset ingestion pipelines or large-scale ETL.
- Frontend web application.
- Complex recommendation algorithms or machine learning.

## 3. Technology Choices

### Selected stack

- Backend framework: FastAPI
- Database: SQLite
- ORM: SQLAlchemy
- Validation and serialization: Pydantic
- Testing: pytest with FastAPI TestClient
- Documentation: OpenAPI/Swagger generated by FastAPI, then exported or converted to PDF

### Rationale

FastAPI is a strong fit because the coursework is API-centric rather than page-centric. It supports clear request and response schemas, automatic validation, automatic OpenAPI documentation, and fast local development. SQLite keeps the project simple and portable for local demonstration, which is important for an oral exam environment. SQLAlchemy makes the relational data model explicit and allows the project to demonstrate database design rather than simple in-memory data handling.

The combination is also defensible in the report and oral Q&A. The trade-off is that SQLite is not ideal for production concurrency, but that is acceptable for this coursework because the system is designed for local demonstration and correctness rather than high-scale deployment.

### Responsibility boundaries

- `routers` will define endpoints and translate between HTTP inputs and service calls.
- `models` will contain SQLAlchemy ORM table definitions.
- `schemas` will define request and response contracts.
- `services` will implement nutrition calculations, search filtering, and cross-model business rules.
- `db` will manage the engine, sessions, and seed data loading.
- `core` will manage configuration and API key verification.

This structure is intended to satisfy the marking emphasis on clean and modular code design.

## 5. Data Model

The system will use three core entities.

### 5.1 recipes

Stores top-level recipe information.

Fields:

- `id`
- `name`
- `description`
- `category`
- `difficulty`
- `servings`
- `instructions`
- `created_at`
- `updated_at`

### 5.2 ingredients

Stores ingredient definitions and their nutrition values per 100 grams.

Fields:

- `id`
- `name`
- `calories_per_100g`
- `protein_per_100g`
- `fat_per_100g`
- `carbs_per_100g`
- `contains_allergen`
- `allergen_notes`

### 5.3 recipe_ingredients

Stores the relationship between recipes and ingredients and records ingredient quantity.

Fields:

- `id`
- `recipe_id`
- `ingredient_id`
- `quantity_g`

### Data model rationale

This design avoids duplicating ingredient nutrition values inside each recipe. It also creates a real relational model rather than a single-table CRUD example. Because quantities are recorded in grams, nutrition totals can be derived by scaling each ingredient’s values from a per-100g basis and aggregating them at the recipe level.

## 6. API Design

The API will use REST-style endpoints and return JSON responses by default.

### 6.1 Public endpoints

- `GET /health`
- `GET /recipes`
- `GET /recipes/{recipe_id}`
- `GET /ingredients`
- `GET /ingredients/{ingredient_id}`
- `GET /recipes/{recipe_id}/nutrition`
- `GET /analytics/recipes/by-category`
- `GET /recipes/search`

### 6.2 Protected endpoints

The following endpoints will require an API key in the `X-API-Key` header:

- `POST /recipes`
- `PUT /recipes/{recipe_id}`
- `DELETE /recipes/{recipe_id}`
- `POST /ingredients`
- `PUT /ingredients/{ingredient_id}`
- `DELETE /ingredients/{ingredient_id}`
- `POST /recipes/{recipe_id}/ingredients`
- `DELETE /recipes/{recipe_id}/ingredients/{ingredient_id}`

### 6.3 Endpoint intent

- Recipe endpoints support creation, retrieval, update, and deletion of recipe records.
- Ingredient endpoints support creation, retrieval, update, and deletion of ingredient records.
- Recipe-ingredient endpoints manage recipe composition.
- Nutrition and analytics endpoints demonstrate value beyond CRUD by performing calculated and aggregated queries.
- The health endpoint provides a simple operational check for local demonstration and deployment verification.

## 7. Validation Rules

Validation will be enforced with Pydantic schemas and service-level checks where needed.

Rules include:

- Recipe names must be non-empty and reasonably bounded in length.
- Category must be non-empty.
- Difficulty must be one of `easy`, `medium`, or `hard`.
- Servings must be greater than zero.
- Ingredient names must be non-empty.
- Nutrition values must be zero or positive.
- Ingredient quantity in a recipe must be greater than zero.

These rules create predictable behavior for both valid and invalid client input and support clearer testing.

## 8. Response and Error Handling

Successful responses will use standard HTTP status codes:

- `200 OK` for successful retrieval and updates
- `201 Created` for successful creation
- `204 No Content` for successful deletion

Error responses will use:

- `400 Bad Request` for domain conflicts or invalid operations
- `401 Unauthorized` for missing or invalid API key
- `404 Not Found` for missing resources
- `422 Unprocessable Entity` for schema validation failures

The project will use a consistent error shape:

```json
{
  "detail": {
    "error": "RESOURCE_NOT_FOUND",
    "message": "Recipe with id 99 was not found"
  }
}
```

Consistent errors will make the API easier to test, document, and explain during Q&A.

## 9. Analytics Features

The project will include the following analytical features.

### 9.1 Recipe nutrition summary

Endpoint: `GET /recipes/{recipe_id}/nutrition`

This endpoint will calculate:

- total calories
- total protein
- total fat
- total carbohydrates
- per-serving values derived from recipe servings

### 9.2 Category counts

Endpoint: `GET /analytics/recipes/by-category`

This endpoint will aggregate recipes by category and return counts for each category.

### 9.3 Filtered search

Endpoint: `GET /recipes/search`

Supported filters:

- category
- difficulty
- maximum calories
- exclude allergens

These analytical endpoints are deliberately included to demonstrate more than minimum CRUD and to strengthen the case for a 70+ grade.

## 10. Authentication Approach

Write operations will be protected with a simple API key passed in the request header. This is intentionally lightweight. It introduces an authentication concept without expanding the project into a full identity system. That trade-off is appropriate for the coursework scope.

The authentication design will be documented in both the API documentation and the technical report. Tests will cover protected and unprotected access paths.

## 11. Testing Strategy

Automated testing will use pytest and FastAPI’s test client.

Core test coverage will include:

- health endpoint success
- recipe creation rejected without API key
- recipe creation success with API key
- missing recipe returns 404
- invalid ingredient payload returns 422
- adding ingredients to a recipe enables correct nutrition calculation
- category analytics returns expected counts
- deleting a recipe makes it unavailable afterward

The test set is intentionally focused on correctness of CRUD behavior, validation, authentication, error handling, and analytics calculations. This is sufficient to demonstrate a systematic testing approach without overscoping the project.

## 12. Data Strategy

The project will use a curated local sample dataset rather than depending on live remote data during the demonstration. This avoids network fragility and keeps the oral examination reliable.

Initial data will include:

- 8 to 12 ingredients
- 5 to 8 recipes
- recipe-ingredient links with realistic quantities

The report will cite the public nutrition references used to derive the sample values. The seed process will populate the local SQLite database for demo and test convenience.

## 15. Risks and Mitigations

### Risk: project scope grows too large

Mitigation: limit the system to recipes, ingredients, relationships, and three analytics endpoints.

### Risk: oral demo fails due to environment issues

Mitigation: keep the project runnable locally with SQLite and provide seed data for fast startup.

### Risk: documentation becomes an afterthought

Mitigation: use FastAPI’s generated OpenAPI docs from the start and align schemas with final documentation output.

### Risk: project looks like only basic CRUD

Mitigation: include nutrition analytics, search filters, authentication, tests, and deliberate modularity.
